# Require character classes in chosen passwords

A chosen password contains 12 to 128 characters and at least one ASCII lowercase letter, one ASCII uppercase letter, one digit, and one symbol from the Supabase Auth set ``!@#$%^&*()_+-=[]{};'\:"|<>?,./`~``, and still differs from the Student ID and the current or temporary password. Core enforces every rule and reports a missing character class with its own error code; the `@showcase/password-policy` package holds the rules Core and every frontend share, so no frontend keeps its own copy and every password-change screen shows the same requirement checklist and strength meter. Submission is gated on the requirements, never on the strength level.

This supersedes the Phase 1 rule that no composition requirement may reject passphrases. The Student app already asked for these classes while the other frontends and Core did not, so the same Person met different rules on different screens and Core accepted passwords a frontend rejected. We rejected keeping passphrase-only acceptance because one Core-enforced policy is simpler to explain and audit than per-surface rules, and we count only ASCII letters, digits, and the Supabase Auth symbol set so the policy matches Supabase Auth's own character classes and a hosted requirement can never be stricter than Core's. We accept that a long lowercase passphrase is now rejected, and that a frontend image older than Core shows a generic unavailable message for the new error code, so Core and every frontend ship from one merge.
