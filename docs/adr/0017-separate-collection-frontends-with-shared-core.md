# Separate document collection frontends while sharing Core

Add two independently deployable frontend applications to the existing monorepo for private form and document collection, one for instructors and one for Students, without adding another backend. The initial four-to-six count omitted the existing media service; the verified deployment inventory has five applications today and seven with these two frontends. Both use the existing Core and database through distinct collection modules and tables, independent of Work, Revision, Review, and publication lifecycles; Core enforces authorization, and each frontend owns a separate surface-bound Authentication Session and host-only cookie under ADRs 0001 and 0003. Share only genuinely reused primitives and contracts. We reject embedding collection in the Showcase frontends or combining instructor and Student collection screens into one application because their workflows and release boundaries differ, and reject a separate repository and duplicated backend to avoid duplicated infrastructure and maintenance. We accept two additional frontend build, deployment, and test targets and the shared failure and backend deployment boundary of Core and the database. Account and Student Roster reuse and instructor identity provisioning were left open when this architecture was selected; subsequent accepted decisions in [the collection scope](../product/phase-1.md#private-form-and-document-collection-accepted-initial-release-scope) reuse Accounts and Student Roster and assign Instructor provisioning and access management to the existing Admin website, with Instructor and Admin remaining separate roles.
