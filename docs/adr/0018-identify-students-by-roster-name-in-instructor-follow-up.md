# Identify Students by Roster name in the Instructor follow-up list

`GET /v1/internal/instructor/students/attention` identifies each outstanding Student by locked Roster first and last name plus the Student's Account ID, and never by Student ID. The Instructor dashboard was specified with a รหัสนักศึกษา column, and exposing Student ID in that one response body was accepted as a scoped exception to the Student ID rule. We did not implement that column: ADR 0013 already removed Core's ability to produce the value. Core retains only keyed HMAC-SHA256 hashes of the full Student ID and of its one-to-seven digit prefixes, so no read path can return a Student ID, and the exception would have required re-introducing reversible storage of authentication data. The Account ID carries the page cursor and every follow-up link, so Student ID stays out of the response body, URL, query string, cursor, log, and client bundle.

We rejected storing plaintext or reversibly encrypted Student IDs to satisfy the column, because Students authenticate with the Student ID and ADR 0013 accepted hashing precisely to remove that credential from Core's readable state. We also rejected displaying a truncated Student ID or a prefix-hash lookup, because a prefix narrow enough to identify a Student is narrow enough to attack the credential, and reversing the hash per row is not bounded work. We accept that an Instructor distinguishes same-named Students by group, form, and deadline rather than by Student ID, and that the roster-identification need is met by Roster name. Restoring the column requires a new decision that first restores a lawful source for the value.
